# GeneralStaff Workbench v2.2 + v2.3 — sealed Fable delta review
Verdict: NEEDS_REVISION
Findings: 3 blocking / 7 advisory

**Reviewer:** Claude Fable (sealed-review seat)
**Date:** 2026-08-28
**Candidate:** delta `59d9cdb..705b488` (`DELTA-59d9cdb..705b488.diff`, 3,707 lines), reviewed against the git-less snapshot in `snapshot/`
**Claims under test:** `docs/GS-WORKBENCH-V2.2-THEMES-EFFORT-PROFILE-NOTE.md`, `docs/GS-WORKBENCH-V2.3-SKILLS-MCP-NOTE.md`
**Posture:** read-only; no files edited, no code executed. The checked-in VSIX was inspected (hash, file listing, string grep) but never installed or run, matching the v2.1 re-verification precedent.

Most of the delta's factual claims survive adversarial cross-checking: the caps math holds, the traversal/symlink rejection is layered and real, skill-keyed session isolation fails closed in every path I could construct, the MCP wiring is mechanically ephemeral (there is not a single filesystem write in `src/`), and effort flags reach every fresh and resumed argv. Three findings block: two are boundary claims stated as guarantees that the code or evidence does not actually establish (the same standard that blocked v2 finding 1 and the v2.1 resume finding), and one is a receipt-honesty defect of the same genre as v2 finding 4. All three are correctable without redesign.

## Release-blocking findings (descending impact)

### 1. Repository-carried code is auto-executed in every direct Codex/Claude run — including read-only runs — with no probe, pin, or consent, contradicting the delta's own trust boundary

**Paths:** `workbench-extension/src/services/privateRuntime.ts:37-49,69-77`; wired unconditionally at `workbench-extension/src/extension.ts:300,393`; claims at `docs/GS-WORKBENCH-V2.3-SKILLS-MCP-NOTE.md:36` and boundary rule at `docs/GS-WORKBENCH-PROFILE-ARCHITECTURE.md` ("The profile must not accept arbitrary command templates, shell fragments, or executable paths … remains subject to the built-in lane probe"; same rule in the v2.2 note).

The v2.3 note claims "MCP definitions are built from verified local executables at run time." "Verified" is three `R_OK` checks (`privateRuntime.ts:44-49`). If `tools/lane-desk/mcp_server.py` is readable in the selected GeneralStaff root, every subsequent direct-Fable and Codex run — read or write — launches `python3 <root>/tools/lane-desk/mcp_server.py --config <root>/lane-desk.toml` as a helper process of the provider CLI (`privateRuntime.ts:71-77`, `cliAdapter.ts:51-58,60-68`). That process runs with ordinary user privileges; nothing in this snapshot shows any sandbox constraining it, and its implementation lives outside the snapshot entirely. `~/.local/bin/headroom-mcp-pure` gets the same treatment on a bare `X_OK` check (`privateRuntime.ts:38,43,70`) — machine-scoped, so less exposed, but equally unprobed.

This is exactly the pattern the delta's own architecture document forbids for lanes: an executable path carried in a repository, imported without a machine-scoped setting, and spawned without the built-in probe discipline every lane binary must pass (`lanes.ts:193-221`). The distinction matters because the GS root is writable by consented lanes: a write-consented Cline run (`--auto-approve true`, `cliAdapter.ts:276-278`) has no OS sandbox — its repository boundary is prompt-and-consent, not enforcement — so a single misbehaving or prompt-injected write run against any sibling repo can plant or modify `tools/lane-desk/mcp_server.py`, and the *next read-only* direct-Fable run silently executes it with full user authority. Before this delta, nothing in the Workbench executed content from the GS root; skills are injected as redacted, capped *data*, which is a categorically weaker privilege. This is new attack surface that converts one repo's write consent into persistent code execution in later read-receipt runs.

**Correction:** gate MCP wiring on something stronger than readability — a machine-scoped allowlist or content pin (hash) for repository-carried server paths, plus a health probe before first wiring, or a one-time host-owned consent modal per executable path (the write-consent modal is the existing pattern). At minimum, stop auto-wiring executables that live inside the selected root and require them to sit at a machine-scoped location like Headroom does.

### 2. The `dontAsk` read-only direct-Fable profile is only ever proven on its allow side; no test or probe demonstrates the deny side the claim depends on

**Paths:** `workbench-extension/src/adapters/cliAdapter.ts:229,244-250`; probes at `workbench-extension/scripts/` (`probe-codex-resume-boundary.ts`, `probe-continuity.ts`, `probe-lane.ts`, `windows-shim-smoke.ts` — no Claude read-boundary probe); claim at `docs/GS-WORKBENCH-V2.3-SKILLS-MCP-NOTE.md:42-47`.

To the direct question — can any configuration path emit a write-capable "read-only" profile? — the answer in the code as written is no: `readOnlyMcp` requires `!writeCapable` (`cliAdapter.ts:229`), the permission-mode ternary cannot produce `acceptEdits` in read mode (`cliAdapter.ts:246`), `--tools Read,Grep,Glob` is emitted in exactly the read+MCP branch (`cliAdapter.ts:244`), and with no MCP servers the original `plan` mode is preserved. The argv construction is sound and unit-tested (`adapter.test.ts:158-183`).

What blocks is the evidence standard. The read guarantee for this profile no longer rests on a provider-enforced mode (`plan`, which denies everything) but on two unverified CLI semantics stacked together: that the installed CLI honors `--tools` as a hard restriction of the built-in surface, and that `dontAsk` denies-rather-than-allows tools outside the six-name `--allowedTools` list (`cliAdapter.ts:70-83`). If either assumption is wrong — or if the two private MCP servers expose *more* tools than the six named, which the allowlist only constrains under deny-by-default semantics — a run whose receipt says "read only" can write. The recorded live smoke (`FABLE_GSWB_MCP_OK lanes=0`) proves an allowlisted call succeeds; it is structurally incapable of distinguishing "restricted profile" from "everything permitted." This is the exact shape of the v2.1 blocking finding, which was resolved by `probe:codex-resume-boundary` — a disposable session that *requests a marker write and verifies denial plus the marker's absence*. No analogous `probe:claude-readonly-boundary` exists.

**Correction:** add a disposable probe that runs the exact production read+MCP invocation (`invocationFor('claude', …, 'read', …, { mcpServers })`), requests a marker write and a Bash command, and passes only when both are refused and the marker does not exist; ideally also call one MCP tool *not* on the allowlist and assert denial. Record its output in the note's evidence the way the codex probe is recorded.

### 3. Receipts claim private capabilities the run did not have

**Paths:** `workbench-extension/src/extension.ts:418-424`; rendered at `workbench-extension/media/workbench.js:467`; contradicting matrix at `docs/GS-WORKBENCH-V2.3-SKILLS-MCP-NOTE.md:31-34` and prompt at `privateRuntime.ts:96`.

`capabilityNames` filters `privateRuntime.capabilities` by `state === 'available'` only — installation state, not lane transport. A Kimi, Cline, Cursor, or Fable-via-Cursor run therefore produces a receipt reading "Headroom + Lane Desk" even though the very same run's prompt told the model "Headroom has no safe native transport in this lane. Do not claim to call it" (`privateRuntime.ts:96`) and the v2.3 matrix declares Headroom "Unavailable" for those lanes. The receipt — a contract pillar this series has blocked on twice (v2 finding 4's static evidence badges; v2.1's resume-boundary honesty) — asserts an attached capability that was never attached, and it flattens "native MCP" and "read-only CLI fallback" into one undifferentiated label for Lane Desk.

**Concrete failure:** operator runs Kimi with Headroom installed; the receipt says the run had Headroom; the operator credits compression/retrieval behavior that could not have occurred, and trusts Lane Desk output as MCP-mediated when it was free-form CLI usage. **Correction:** filter by the effective lane/runner against `nativeLanes`/`fallbackLanes` (both already computed in `PrivateCapabilitySummary`), and label fallback usage distinctly (e.g. "Lane Desk (CLI fallback)").

## Advisory findings (non-blocking)

1. **Skill metadata and the bundle preamble bypass redaction, and the advertised 260k cap excludes the preamble.** `compileSkillBundle` redacts file sections (`skills.ts:176`) but the frontmatter-derived name/description flow unredacted to the webview catalog and receipt (`skills.ts:130-143`, `domain.ts` SkillSummary), and the compatibility preamble embeds the unredacted absolute source directory (`skills.ts:183`). Total prompt = preamble + capped sections, so it slightly exceeds the stated 260,000 characters. All marginal — skill frontmatter is operator-authored — but the note's "redacted before dispatch" is not literally total.
2. **No per-file size cap before reading.** `textFiles` reads entire files (`skills.ts:106`) and `discoverSkills` does this for every text file of every skill on every fleet refresh (`skills.ts:147-163`, `fleet.ts:291-294`); the 80/260k caps apply only after full reads. One accidental multi-hundred-MB `.json` companion stalls or OOMs every refresh. Check `stat.size` before reading and cap per file.
3. **Hard links are not rejected.** Symlinked entries and directories are excluded at both layers (`skills.ts:96,126,157`) and the relative-path guard holds (`skills.ts:105`), but a hard-linked file inside a skill directory bundles out-of-tree content from the same filesystem with redaction as the only backstop. Low severity given the operator-owned source tree; worth a note in the claim language.
4. **Prompt-as-argv lanes can now exceed platform argument limits.** Claude `-p`, Kimi `-p`, and Cline/Cursor positional prompts (`cliAdapter.ts:232,262-263,284,300`) can carry ~372k characters (80k operator text + 30k transcript + 260k bundle + preamble) in a single argv element. Fine on the target macOS (1 MB ARG_MAX); hard-fails on Linux (128 KiB per-arg) and the Windows shim path. Failure is a visible spawn error, not silent, hence advisory. Codex is immune (stdin). Prefer stdin where the CLI supports it.
5. **The packaging evidence chain is broken at HEAD.** The checked-in VSIX hashes `bd6cd8f82457fc450fcb681e5d84ce50322c2201a27c0d45bb39eeb0d643e122` (10 files; I verified it contains the 0.2.3 code — `dontAsk`, `mcp_servers`, skill-contract markers, `"version": "0.2.3"`). No note records this hash or a clean-profile install for 0.2.3; the v2.2 note's recorded hash (`089877b3…`) no longer matches the artifact. The v2.3 note honestly omits packaging claims, but the shipped artifact's provenance should be re-recorded per the series' own practice.
6. **Exposed effort values are asserted argv-only, never proven per value against live providers.** `model_reasoning_effort="xhigh"` (codex, `cliAdapter.ts:180,201`), `--effort xhigh` (claude, `cliAdapter.ts:247-248`; v2.1 only ever ran high/max live), and `--thinking none|xhigh` (cline, `cliAdapter.ts:280-281`) have exact-argv tests but no recorded live acceptance probe per value. A provider that errors fails visibly; a provider that warns-and-defaults would silently not apply the selected effort while the receipt records it as effective — the one residual "silent effort" path I could find. A one-time live matrix probe closes it.
7. **A slash-invoked skill switch persists before the send is validated.** `startRun` commits `setSkill` (`extension.ts:281-284`) before the lane availability/effort check (`extension.ts:285-293`); a rejected send still re-keys the conversation's skill and thereby discards native continuity for the next successful send. Move the mutation after validation.

## Priority-surface verdicts

**Skills bridge (surface 1).** The caps hold under attack: `maxBundleFiles` is enforced at both loop levels (`skills.ts:83,96`), SKILL.md is deterministically slot 1 (`skills.ts:90-94`), and the character budget is arithmetic-tight — `redact(content, remaining)` redacts over the *full* content and truncates after (`redaction.ts:15-21`), so a secret straddling the truncation boundary is already replaced; sections sum ≤ 260,000 (`skills.ts:172-179`). Traversal is closed by the id pattern at three independent layers (bridge validator `messages.ts:32-35`, slash parser `skills.ts:209`, loader `skills.ts:118`), so `path.join(root, 'skills', id)` cannot escape; symlinked skill directories, entries, and subdirectories are rejected (`skills.ts:96,126,157`), with tests (`skills.test.ts`, `messages.test.ts` `../audit` rejection). The `lean-ctx` tombstone is excluded end-to-end (`skills.ts:118,157` plus unknown-slash rejection). Redaction now includes the JWT pattern the v2 review requested (`redaction.ts:7`); bare 64-hex secrets remain uncovered, consistent with the documented best-effort posture. Session isolation is skill-keyed and fails closed in every path I constructed: lookup requires exact `runner`/`permission`/`skillId`/`cwd` match (`conversations.ts:156-173`), a mid-conversation skill change misses the stored key and degrades to transcript (which carries only visible messages, not the hidden bundle), legacy runner-less sessions fail closed (tested), and the "already loaded in this provider session" reminder (`extension.ts:332-333`) is sound because a native hit *implies* the bundle was sent when that session was created under the same key. Residuals are findings 1-3 (advisory) above.

**MCP ephemerality (surface 2).** Mechanically verified: definitions travel only as per-invocation argv (`-c mcp_servers.…` for codex, inline-JSON `--mcp-config` for claude, `cliAdapter.ts:51-68`); there is no `writeFile`/`mkdir`/stream write anywhere in `src/` (checked); persistence surfaces are VS Code `globalState` and the machine-scoped `rootPath` setting only. Non-native lanes never receive the definitions — kimi/cline/cursor and the Fable-via-Cursor branch ignore `mcpServers` entirely (`cliAdapter.ts:212-227,255-304`), with a test asserting the negative (`adapter.test.ts:176-182`). The unrefutable remainder is what the servers *do*, which is out-of-snapshot — finding 1 (blocking) covers how they get to run at all.

**Read-only direct-Fable profile (surface 3).** No configuration path in this code emits a write-capable read profile; the residual risk is CLI-semantics, unproven on the deny side — blocking finding 2.

**Effort + themes (surface 4).** No lane silently drops a selected effort in this code: effort reaches codex fresh *and* resume argv (`cliAdapter.ts:178-180,200-201`), claude direct fresh and resume via the single shared return (`cliAdapter.ts:247-248`), Fable-via-Cursor as the model suffix on fresh and resume (`cliAdapter.ts:215-217`, `adapter.test.ts:193-200`), and cline fresh (resume is refused outright, `cliAdapter.ts:271-273`). Kimi/Cursor expose only `default` and say so honestly in label and receipt. Validation is genuinely triple-layered (webview `ensureSelections` `workbench.js:123-126`; bridge `messages.ts:22,54-55,83`; host `extension.ts:135-139,174-179,285-293`; adapter throw `cliAdapter.ts:97-100`), and the receipt records the effective value (`cliAdapter.ts:566-567,574`). Themes: all six palettes exist in CSS and the picker, ids are allowlisted before application (`workbench.js:142-148`), names are escaped, selection persists in webview state, and the hardcoded-alpha sweep is test-enforced (`themes.test.ts`). The only effort residual is the provider-side value-acceptance gap (advisory 6).

**Undocumented delta items (surface 5).** Checked and benign: `redact()` gained a `maxLength` parameter (defaults preserve v2 behavior); stream parsing and session-id extraction switch on the effective runner (`protocolLaneId`, `cliAdapter.ts:487,525,537`); Fable-via-Cursor write mode uses `--force` in parity with the plain Cursor lane; `engines.vscode` and `@types/vscode` are now aligned at `^1.134.0` (resolving v2 finding 5 by lowering the engine rather than raising the types); the `initialSessionId` pre-allocation is correctly gated to the direct-claude runner (`cliAdapter.ts:476-478`); probe scripts and the visual harness were updated for the new required fields. The fleet-test capability assertion (`fleet.test.ts:47`) is vacuous — `capabilities` always contains a lane-desk entry regardless of state — worth tightening but not a finding. Test inventory: 38 across ten files, matching the v2.3 note exactly.

## What was verified and holds

Message validation rejects invented efforts and malformed/traversal skill ids (`messages.test.ts`); unknown `/slash` procedures are refused with an operator-visible notice rather than passed through (`extension.ts:267-274`); the update-routing run-lock still covers the new effort/skill fields and re-checks after the consent await (`extension.ts:166-169,195-198`); the pendingRuns reservation, write-consent modal, discovered-repo requirement, Kimi read refusal, read-default resets on every new-conversation path, CSP (`default-src 'none'`, nonce, `connect-src 'none'`), argv-array spawning with no `shell: true`, output/evidence caps, and provider-session UUID redaction all remain intact from v2/v2.1. The v2 root-mapping guard test (`never maps a state project back to the private root`) is still present and unmodified. `npm run check`, `npm audit`, the live discovery results, the live Codex config probe, and the direct-Fable smoke are accepted as reported execution evidence, not re-run (read-only posture). The Lane Desk and Headroom implementations are outside this snapshot; every claim about their internal behavior ("strictly observational," "pure MCP mode") is accepted as asserted only, which is precisely why findings 1 and 2 demand mechanical rather than narrative guarantees.

The three blocking items each have small, well-scoped fixes: a wiring gate plus probe for repository-carried MCP executables, a deny-side read-boundary probe for the `dontAsk` profile, and a one-line lane-transport filter on receipt capabilities. None invalidates the v2.2/v2.3 design.
